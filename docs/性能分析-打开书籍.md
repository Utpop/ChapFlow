# 打开书籍的性能分析（ChapFlow 1.2.22）

> 场景：同一个窗口里反复「打开另一本书」。
> 结论先说：**没有发现泄漏**——反复打开 15 次后，Session / EpubBook 各只有 1 个，控件、QAction、QThread、QTimer 数量完全不变。
> 真正拖慢打开的是 **三处「每次都重建界面」的无谓工作**，加上 **整本书字节常驻内存** 这一项内存开销。

---

## 1. 测量环境与方法

- 机器：Windows 11，Python 3.15，PySide6（离屏 `QT_QPA_PLATFORM=offscreen`，窗口 1400×900）
- 样本：`book3`（4 章，4 KB）；`300 章 / 194 KB`；`300 章 / 4 MB 文本`（压缩后 0.2 MB）；`1000 章`
- 方法：
  - 从 `load()` 发起到 `self.session` 换上新对象为止计一次「打开」；
  - 逐段包一层计时（`_apply_expansion` / `_load_preview` / `_update_actions` / `tree.setCurrentIndex` …）；
  - 内存用 `GetProcessMemoryInfo` 读 Working Set；
  - 泄漏用 `gc.get_objects()` 数 `Session / EpubBook`、控件、QAction、QThread。

---

## 2. 数据

### 2.1 单次打开耗时

| 书籍 | 打开一次（稳定段） | 其中「选中首项 + 预览」 | `expandAll` | `_update_actions`（一次打开跑 3 遍） | 后台解析 `Session()` |
|---|---|---|---|---|---|
| 4 章 / 4 KB | 15–37 ms | 1.5 ms | 0.6 ms | 1.8 ms | ≈5 ms |
| 300 章 / 194 KB | 100–148 ms | **26.5 ms** | **16.7 ms** | 2.8 ms | 16.5–25 ms |
| 300 章 / 4 MB 文本 | ≈208 ms | **70.3 ms**（预览占 36.3） | 27.1 ms | 4.8 ms | — |
| 1000 章 | — | — | **43–103 ms** | — | — |

> 另有约 40–60 ms 无法归到上面几段：线程启动/销毁、跨线程信号、以及打开后首帧重绘（离屏平台同样走软件绘制）。

### 2.2 内存

| 操作 | RSS 变化 |
|---|---|
| 打开 3 MB（不可压缩）书 | +3.9 MB |
| 打开 10.2 MB（5×2 MB 图片）书 | **+11.1 MB** |
| 同一本 10 MB 书连开 3 次 | +11.1 → 85.9 → 85.9 → 86.0（**不累积**） |
| 从 10 MB 书切回小书 | 85.9 → 76.0（**会释放**，余 1.2 MB 是分配器缓存） |
| 1000 章书上做 30 次编辑 | +0.02 MB/步（撤销快照，100 步上限 ≈ 2 MB） |

### 2.3 泄漏相关计数（打开 1 次 vs 15 次）

```
打开1次   widgets=124  actions=39  threads=0  timers=0  Session=1  EpubBook=1
打开15次  widgets=124  actions=39  threads=0  timers=0  Session=1  EpubBook=1
```

**结论：没有控件/监听器/线程/定时器累积，也没有旧 Session 泄漏。**
（`_run()` 里 `finished → deleteLater()` 的清理是有效的；`QAction`/`QShortcut` 只在 `__init__` 建一次。）

## 3. 瓶颈逐项分析

### B1. 每次打开都 `expandAll()`（P0，最稳的收益）

- **位置**：`MainWindow.done()` → `_apply_expansion(set(), expand_all=True)` → `tree.expandAll()`（`main_window.py`）
- **现象**：不管书多大、用户想看哪一章，一律把整棵树全展开。
- **证据**：300 节点 17–68 ms、1000 节点 43–103 ms；profile 显示 5 次打开里 `expandAll` 141 ms，`model.index()` 被调用 8445 次、`flags()` 4870 次——展开每行都要建 `QModelIndex`（`models.index()` 里还带一次父链查找）再经 proxy 映射。
- **建议**：
  1. 改成 `tree.expandToDepth(1)`（只展开到第一层，用户点开再看下一层）；
  2. 顺带把 `_expanded_uids()` 已有的「按 uid 恢复展开」用于**记住每本书上次的展开状态**（存 QSettings，键用书籍路径），打开时只恢复这些节点。
- **预期收益**：300 章 −10~17 ms，1000 章 −30~60 ms（约等于打开总时长的 25–40%）；同时首帧要绘制的行数大幅减少。

### B2. 打开时立刻选中首项，连带渲染预览（P0，文本量越大越明显）

- **位置**：`done()` 里 `self.tree.setCurrentIndex(self.proxy.index(0, 0))` → 触发 `selectionChanged` → `_update_parent_info` + `_load_preview`（把章节正文 + 图片塞进 `QTextBrowser`）+ 又一次 `_update_actions`。
- **证据**：300 章 26.5 ms；4 MB 文本书 70.3 ms，其中 `_load_preview` 占 36.3 ms；单独连点 10 次选中项 72.6 ms。
- **建议**：
  1. 打开时只设「当前项」、**推迟渲染**：用 `_suppress_preview = True` + `QTimer.singleShot(0, self._sync_preview)`，让首帧先出来；
  2. 预览面板不可见（`detail_empty` 显示中）时直接跳过渲染；
  3. 切书时先 `preview_view.clear()`，避免拿旧文档做差异对比。
- **预期收益**：−20~60 ms；「点开书」到「界面出现」的感知延迟明显改善（重文本更明显）。

### B3. `_update_actions()` 在一次打开里跑 3 遍（P1）

- **证据**：5 次打开共 15 次调用；300 章 2.8 ms/次、4 MB 文本 4.8 ms/次 → 一次打开 8~15 ms。
- **来源**：`done()` 显式一次 + `_refresh_counts()`/`_update_empty_state()` 各触发一次 + 选中变化一次。
- **建议**：合并成「脏标记 + `QTimer.singleShot(0)`」只跑一次；或拆成两组：只随会话变的（打开/关闭按钮）与只随选中变的（上下移/删除）。
- **预期收益**：−6~12 ms。

### B4. 整本书的字节常驻内存（P1，内存最大项）

- **位置**：`EpubBook.__init__`：`self.raw = f.read()`，`ZipFile(io.BytesIO(self.raw))`，并一直持有到会话结束（`raw` 还用于 `info()["size"]`）。
- **证据**：3 MB 书 → +3.9 MB，10 MB 书 → +11.1 MB（≈文件大小）；且切书后能释放，说明只是「当前书」占着。
- **风险**：200 MB 图文书 → 常驻 200 MB；如果再开着阅读器看旧书，旧书也驻留（见 B7）。
- **建议**（二选一）：
  - **按需打开**：只留 `path`，`read(name)` 时用短生命周期的 `zipfile.ZipFile(path)`；`size` 用 `os.path.getsize`。注意 `save_in_place()` 用 `os.replace` 覆盖原文件，写盘前必须先关句柄；
  - **mmap**：`mmap.mmap(f.fileno(), 0, access=ACCESS_READ)` 后交给 `ZipFile`，让 OS 按页调入——RSS 只随「真正读到的条目」增长。
- **预期收益**：内存 −(书的大小)，10 MB 书 −9 MB、200 MB 书 −190 MB；代价是解析 +2~5 ms（重开 zip）。

### B5. 每次打开新建一个 `QThread`（P2）

- **位置**：`_run()` 里的 `Worker(fn, self)`。
- **影响**：线程创建/销毁 + 跨线程信号 1~3 ms；连点会命中「上一个任务还在进行，请稍候」。
- **建议**：换 `QThreadPool` + `QRunnable`（Qt 自带，线程复用），或保留一个常驻 worker 用队列派活。
- **预期收益**：−1~3 ms，并减少线程对象抖动。

### B6. 目录遍历重复（P2）

- `done()` 里 `_refresh_counts()` 和状态栏文本各调一次 `CF.count_nodes(toc)`（都是 O(n)）。
- **建议**：把 counts 缓存到 `Session`，`refresh()/toc 变更` 时失效。
- **预期收益**：1000 章约 −2 ms。

### B7. 阅读器窗口会「拖住」旧书（P1，内存）

- **位置**：`open_reader()` 把窗口放进 `self._readers`；`load()` 切换书籍时**既不关闭也不清理**这些窗口。
- **额外问题**：`_on_select` 里有 `self._readers = []`（`main_window.py` ≈842 行），把登记表清空，之后 `_forget_reader` 找不到它，语义混乱。
- **影响**：看大书 → 开阅读器 → 切到小书，大书的 `raw` 仍被阅读器持有的 session 引用着。
- **建议**：`load()` 开头统一 `for w in self._readers: w.close()`（或提示「先关闭阅读窗口」），并删掉 `_readers = []` 那一行。
- **预期收益**：避免「切书后内存不降」，最坏情况可省下一整本书。

### B8. 导出/保存时把整本书读进一个 dict（P1，瞬时内存）

- **位置**：`export_epub()` 开头 `for name in order: files[name] = book.read(name)`。
- **影响**：保存 200 MB 书瞬时 +200 MB（与打开路径叠加，容易触发系统换页）。
- **建议**：改成逐个 `zf.writestr(name, book.read(name))` 流式写，不建全量 dict；未修改条目可以直接 `zf.open(name)` 复制。
- **预期收益**：保存的峰值内存从 2×书 降到 ≈1 条目。

### B9. 撤销快照（实测不是问题，记录备查）

- `_snapshot()` = `clone_toc` + `dict(new_files)` + `opf_text`。`new_files` 是浅拷贝（bytes 共享），所以不会复制图片。
- 实测 1000 章 0.02 MB/步；唯一副作用：被删掉的 `new_files` 条目要等快照被挤出（≤100 步）才真正释放。

## 4. 建议的实施顺序

| 优先级 | 项 | 改动范围 | 预期收益 | 状态 |
|---|---|---|---|---|
| **P0** | B1 只展开一层 + 记住展开状态 | `main_window._apply_expansion` | 大书 −30~60 ms（25–40%） | ✅ 已落地 |
| **P0** | B2 预览延迟到首帧后 | `main_window.done/_load_preview` | −20~60 ms，感知更快 | ✅ 已落地 |
| **P1** | B3 合并 `_update_actions` | `main_window` | −6~12 ms | ✅ 已落地 |
| **P1** | B7 切书关闭旧阅读器 | `main_window.load/open_reader` | 避免旧书驻留 | ✅ 已落地 |
| **P1** | B4 不再常驻整本字节 | `chapflow.EpubBook` | 内存 −(书大小) | ✅ 已落地（mmap） |
| **P1** | B8 流式导出 | `chapflow.export_epub` | 保存峰值内存 −(书大小) | ✅ 已落地 |
| **P2** | B5 线程池、B6 计数缓存 | `main_window` / `Session` | −3~5 ms | ✅ 已落地 |

只做 P0 的两项，300 章书的打开时间可从 ~150 ms 降到 ~90 ms；4 MB 文本的 ~208 ms 降到 ~120 ms。

---

## 5. 验收标准

改动后复测同一套探针，应满足：

1. 300 章书打开 **< 100 ms**、1000 章 **< 150 ms**（本机离屏、1400×900）；
2. 打开 10 MB 图文书，RSS 增量 **< 3 MB**（B4 落地后）；
3. 连续打开 15 次后 `widgets / actions / threads / timers / Session` 计数与第 1 次完全一致（现状已达标，作为回归项保留）；
4. 切换到较小的书后 RSS 回落到接近切换前水平（差值 < 3 MB）。

## 6. 实施结果

八项全部落地（改动集中在 `src/ui/main_window.py`、`src/chapflow.py`），复测脚本固化为
`tools/bench_open.py`（离屏、1400×900；`--repeat N` 控制重复次数）。

### 6.1 打开耗时（复测同一套探针）

| 书籍 | 改造前（§2.1） | 改造后 | 变化 |
|---|---|---|---|
| book3（4 章 / 4 KB） | 15–37 ms | **11.9 ms** | −60% |
| 300 章 / 194 KB | 100–148 ms | **38.7 ms** | −62% |
| 300 章 / 4 MB 文本 | ≈208 ms | **52.6 ms** | −75% |
| 1000 章 | —（仅 expandAll 就 43–103 ms） | **110.3 ms** | expandAll 已降到 0.4 ms |

分段（300 章）：`_restore_expansion` 0.2 ms、`_load_preview` 1.1 ms、`_update_actions` 0.5 ms、
`_refresh_counts` 0.1 ms —— 剩下的主要是 Qt 布局与首帧绘制，属于「必须画出来的行」。

### 6.2 内存

| 场景 | 改造前 | 改造后 |
|---|---|---|
| 打开 10 MB 图文书 | +11.1 MB | **−0.9 MB（噪声范围内，mmap 按页调入）** |
| 从大书切回小书 | 回落但有 1.2 MB 余量 | 回落，差值 −0.8 MB |
| 保存 4 MB 文本书的峰值 | 再吃一遍整本解压后的文本 | **+0.0 MB**（逐条流式写入） |

### 6.3 具体做法

| 项 | 实现 |
|---|---|
| B1 | `_restore_expansion()`：≤80 项全展开，超过则恢复上次的展开路径（`QSettings`，键为书籍路径的 md5，存 `{"paths": ["1.3", …]}`），首次打开 `expandToDepth(0)`；`_apply_expansion(uids, …)` 去掉「uids 为空就全展开」的兜底（原来折叠全部后再改名会整本重展开） |
| B2 | `_schedule_preview()` + `QTimer.singleShot(0, _flush_preview)`：选中只登记，渲染留到下一轮事件循环，连续切换自动合并成一次；切书时先 `preview_view.clear()` |
| B3 | `_batched()` 计数器 + `_actions_dirty`：`done()` 与 `_run` 的 `ok()` 都包一层，一次打开里的 3~4 次刷新合并成 1 次 |
| B5 | `Worker` 由 `QThread` 改为 `QRunnable` + `WorkerSignals`，投递到 `QThreadPool.globalInstance()` |
| B6 | `Session.counts()` 缓存（`push` / `_restore` 失效，另用「顶层数 + 顶层子项数」做廉价校验），界面改用它 |
| B7 | `load()` 开头关闭所有阅读器窗口；删掉 `_on_selection_changed` 里误清空 `self._readers` 的一行 |
| B4 | `EpubBook` 用 `mmap.mmap(..., ACCESS_READ)` + `ZipFile(mm)`，不再 `f.read()`；`info()["size"]` 取 `os.path.getsize`；新增 `close()/reopen()`，`read()` 遇到已释放会按需重开；`_LIVE_BOOKS` 登记所有打开的书写，覆盖保存前统一松手、写完再逐个重映射 |
| B8 | `_BookFiles`（`MutableMapping`）：`in / [] / del` 用法不变，内容按需从 ZIP 解压且不缓存；打包时未修改条目用 `zf.open(..., "w") + shutil.copyfileobj` 流式复制 |

### 6.4 回归

- 断言：引擎 **514**、界面 **408**、审计 **190**、LLM 切分 **86**，全部通过；
- 连开 15 次后 `widgets / actions / threads / timers / Session / EpubBook` 计数与第 1 次完全一致；
- EPUBCheck：单书导出 / 合并 / 脏书修复 / EPUB2 修复四条产线 **0 error**。

### 6.5 剩余热点（如果还要再快）

1. 1000 章 110 ms 里约 80 ms 是 QTreeView 自身的布局 + 绘制 1000 行（`uniformRowHeights` 已开）；
   要再降需要把目录做成「按需展开的懒加载模型」（只对可见区域提供 `rowCount`），改动较大。
2. 大文本章节的预览渲染（4 MB 书 12.6 ms）可以用增量渲染 / 只渲染可见段落再压一半，但收益有限。
