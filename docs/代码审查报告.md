## 一、llmseg.py（LLM 辅助章节切分）

整体设计良好：只外发候选行而非全文、失败回退本地规则、结果护栏（`_guard`）、候选序号白名单校验，`to_dict` 默认不含密钥。以下为改进点：

### [P1-安全] API Key 明文落盘 【已修复】
- **位置**：`llmseg.py:274-286`（`LLMOptions.save`，默认 `with_key=True`）
- **问题**：密钥以明文 JSON 写入 `%APPDATA%\ChapFlow\llm.json`。同机恶意进程/备份同步/用户共享目录都可能读走。
- **建议**：默认 `with_key=False`（密钥仅走环境变量）；确需落盘时用 Windows DPAPI（`ctypes` 调 `CryptProtectData`）加密 `api_key` 字段，并在 UI 中明示"密钥将以加密形式保存在本机"。
- **修复（2026-11-01）**：`llmseg.py` 新增 `_protect_secret` / `_unprotect_secret`（DPAPI，CurrentUser，无 UI 弹窗）；落盘写 `api_key_enc` 密文字段（平台无 DPAPI 时回退明文保证可用），`from_dict` 自动解密，旧版明文配置仍可读取；GUI 提示改为"密钥经系统加密（DPAPI）后保存"。回归断言在 `test_llmseg.py::test_config`（Windows 下断言不明文落盘）。

### [P2-安全] base_url 无协议校验，可读本地文件片段
- **位置**：`llmseg.py:179`（`normalized` 不校验 scheme）、`llmseg.py:384-398`（`endpoint`）、`llmseg.py:515`（错误信息含 `raw[:160]`）
- **问题**：`base_url` 可填 `file:///C:/...` 等。urllib 对 `file://` 的 POST 请求会直接读取本地文件，文件内容片段会经 `LLMError("回复不是合法 JSON：%s" % raw[:160])` 泄露到错误弹窗。
- **建议**：`normalized()` 中强制 `base_url` 以 `http://` 或 `https://` 开头，否则清空并让 `problem()` 报"服务地址必须是 http(s)"。

### [P2-安全] 响应体无大小上限
- **位置**：`llmseg.py:498-499`（`fh.read()` 无限制）
- **问题**：恶意/失控服务端可返回任意大响应，撑爆内存。
- **建议**：`fh.read(2_000_000 + 1)` 并对超长响应报 `LLMError("响应过大")`。

### [P2] from_dict 对字符串布尔值解析错误
- **位置**：`llmseg.py:229-231`
- **问题**：手改配置 `"enabled": "false"` 时 `bool("fals")` 为 `True`，意外开启联网。
- **建议**：复用 `from_env` 的开关判断（`str(v).strip().lower() not in ("0","false","off","no","")`）。

### [P2] 超时被误报为网络不通
- **位置**：`llmseg.py:506-509`
- **问题**：urllib 常把超时包在 `URLError` 里抛出，提示"连不上服务器"，误导排障。
- **建议**：`except urllib.error.URLError` 里判断 `isinstance(exc.reason, (TimeoutError, socket.timeout))`，分开提示。

### [P2] `_judge_batch` 的 `except Exception` 过宽
- **位置**：`llmseg.py:876-881`
- **问题**：把编程错误（AttributeError/TypeError）也吞成 `LLMError` 降级，掩盖真实 bug。
- **建议**：仅捕获 `LLMError / OSError / ValueError`，其余异常放行（或在开发模式下 re-raise）。

### [P2] 兜底解析正则宽松，行内误匹配
- **位置**：`llmseg.py:557, 704`（`_KV_NUM` 匹配行内任意 `i=3`）
- **问题**：模型输出散文时，正文里的 `i=3` 等字样会被当成一条决策。
- **建议**：要求行首锚定（`^`）或整行匹配后再取序号。

### [P2] `refine_marks` 的 kwargs 透传不严谨
- **位置**：`llmseg.py:1029`
- **问题**：`hasattr(LLMOptions, k)` 对方法名也成立，传入 `normalized=...` 等会 TypeError。

## 二、xmldom.py（保真 XML DOM）

无外部实体解析（不存在 XXE 面），未定义实体保留原文，畸形输入有前进保证——安全性基础好。

### [P1] 数字字符实体可产出孤立代理对，导出时崩溃 【已修复】
- **位置**：`xmldom.py:98-103`（`_decode_entities` 中 `chr(code)`）
- **问题**：`&#xD800;`~`&#xDFFF;` 会生成孤立 surrogate 字符；后续任何 `.encode("utf-8")`（导出 zip 写入）抛 `UnicodeEncodeError`，恶意/损坏 EPUB 可让导出崩溃。
- **建议**：
  ```python
  code = int(body[2:], 16) if body[1:2].lower() == "x" else int(body[1:])
  if 0xD800 <= code <= 0xDFFF or code > 0x10FFFF or code <= 0:
      return m.group(0)      # 不可解码实体原样保留
  return chr(code)
  ```
- **修复（2026-11-01）**：按上述方案修改 `_decode_entities`，拒绝时置 `raw` 标记使序列化保留实体原文（如 `&#xD800;`）；回归测试在 `run_tests.py::test_review_fixes`（[33] 组，含越界码位 `&#x110000;`）。

### [P2] 序列化/遍历递归无深度保护
- **位置**：`xmldom.py:276-293`（`serialize_xml`）、`314-323`（`text_of`）、`326-331`（`walk`）
- **问题**：`parse_xml` 是迭代实现，但输出侧是递归；数万层嵌套的畸形 XML 会 `RecursionError`。
- **建议**：统一转为显式栈迭代，或在 `parse_xml` 里限制嵌套深度（如 256 层，超出按文本保留）。

### [P2] `X.set()` 与 `X.get()` 匹配语义不一致
- **位置**：`xmldom.py:75-80`
- **问题**：`set("href")` 会命中并覆盖 `epub:href` 这类同 local-name 属性；`get("href")` 则要求全名相等，二者不对称，易在改 OPF 属性时写错对象。
- **建议**：`set` 只精确匹配全名（新增属性也用全名），或提供显式 `set_loose()`。

### [P2] 撤销快照与历史深度相乘，内存放大
- **位置**：`chapflow.py:1681-1700`（每步 `clone_toc` + `dict(new_files)`，保留 100 步）
